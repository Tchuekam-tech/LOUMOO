# LOUMOO — URLs and routing

Every major area of LOUMOO has a stable URL under the production domain
(`https://loumoo.store`). You can open it directly, refresh it, bookmark it, share it, and — when it
needs an account — sign in and be brought back to it.

The single source of truth for those URLs is **`src/routing/routes.js`**. This document is the
prose around it; the route map in section 2 is generated from it.

---

## 1. How it works

LOUMOO is one HTML document (`Commerce App.dc.html`, generated by `build_redesign.py`) running on a
custom Design-Component runtime (`support.js`, React underneath). Its screens are not pages: the
shell shows whichever one `state.screen` names. Before this work nothing connected that state to the
address bar — every address returned the home page, nested addresses broke the app's own relative
asset paths, and the rider/seller/tracking tools were overlays no URL could open.

```
 src/routing/routes.js        the registry: every URL, what it opens, who may open it   (browser + Node)
        │
        ├── src/services/appRouter.js   the History-API router (window.LoumooRouter)
        │        URL → screen        on load, refresh, back/forward, link clicks
        │        screen → URL        after every shell state change
        │        overlays            /rider, /delivery/:id, /sell/deliveries … open and close with the route
        │        access              asks the existing account guard (src/services/accountGuard.js)
        │
        ├── build_redesign.py  ("URL routing" block)   the adapter that lets the router drive the shell
        ├── server/index.js                            the gateway: shell / 404 / redirects (Railway, local)
        └── scripts/sync_route_config.js               generates vercel.json
```

Rules the design keeps:

* **One navigation system.** `window.LoumooRiderHub.open()`, `LoumooSellerDispatch.open()`,
  `LoumooDeliveryTracking.open()`, `LoumooProviderProfile.open()` and `LoumooRidersAdmin.open()` still
  exist, but with the router active they only navigate to the canonical URL; the route then calls the
  module's internal `mount()`. Nothing opens a tool behind the router's back.
* **State drives the URL, the URL drives state — never both at once.** URL changes (load, back/forward,
  link click) are applied to the shell through the adapter. Shell changes (`go()`, `openProduct()`, …) are
  mirrored to the address bar after the fact, so every existing in-app flow keeps working unchanged.
* **The client guard is a convenience, not a security boundary.** See section 7.

## 3. Behaviour

**Direct load and refresh.** The gateway hands the application shell to every registered URL (HTTP 200).
The router reads `location`, applies the access policy, and shows the screen — so refreshing
`/store/acme` stays on `/store/acme`. While a protected route's account state is being resolved the
shell shows its skeleton, not the home page.

**Steps of an in-memory flow** (checkout success, a half-filled booking, onboarding step 4…) cannot be
rebuilt from a URL. They are marked `direct: 'redirect'` in the registry: a cold load or refresh sends
the visitor to the route that can continue (e.g. `/checkout/success` → `/orders`). Back/forward *within
a session* still works.

**Back / forward.** Every place the visitor passes through gets a history entry; the browser buttons and
the in-app Back buttons both step through them. In-app Back uses `history.back()` when the tab has an
earlier entry, otherwise it climbs to the route's `parent`. Record canonicalisation right after a URL open
(`/store/<id>` → `/store/<slug>`) replaces the entry instead of adding one.

**Sign-in and return.** A signed-out visitor on a protected URL is replaced (not pushed) by
`/sign-in?returnTo=<path>`; the same destination is remembered in `localStorage`
(`loumoo_post_auth_intent`, one hour) so it survives the forgot-password and verification detours. After
sign-in, email verification or onboarding the shell asks the router for it and navigates there with the
exact record (`/orders/42?tab=items`). `returnTo` is accepted only if it is a same-origin path that
resolves to a registered, non-authentication route (`Routes.safeReturnTo`): no `//host`, no scheme, no
backslash, no control characters, no unknown path, never `/sign-in` itself.

**Account states** (from `GET /api/v1/me/state`, the backend state machine in
`server/modules/identity/domain/AccountState.js`): an unverified account is sent to `/verify`, one
without onboarding to `/onboarding`, a boutique-in-progress seller to `/sell/create-store` or
`/sell/onboarding`, each with the server's own explanation and the original destination remembered. A
**suspended** account — which the server answers with HTTP 403 — lands on `/account/suspended` with a
clear message, not in a sign-in loop. A **network failure** while resolving the state lets the attempt
through (the server is the real gate and answers every request correctly). Redirect chains are capped at
five hops.

**Overlays.** `/rider`, `/delivery/:id`, `/orders/:id/tracking`, `/sell/deliveries[/:orderId]`,
`/providers/:id`, `/account/following/providers` and `/admin/riders` open a full-window tool over a
real screen. Dismissing it (Done, Esc, scrim, its own close button) leaves the route: back one entry
when there is one, otherwise up to the parent. Browser Back closes it.

**Not found.** Anything the registry does not know is HTTP 404 *with the application*, which draws a
deliberate "Page not found" screen at the visitor's own URL (`noindex`). A record that does not exist or
is not the visitor's (`/store/zzz`, `/orders/<someone else's>`, `/delivery/<someone else's>`) shows the
same screen. An account that may not open an area sees "You do not have access". `/markethub` and
`/agency` say "not available yet". A fetch error on a record shows "We could not load this page" with a
retry — never a blank page.

## 4. Assets work from any depth

The shell's relative references (`./src/...`, `./Assets/...`, `./support.js`, the `*Screens.dc.html`
chunks the runtime fetches, `data/catalog.json`, design-system CSS) used to resolve against the
*current URL*. On `/store/acme` they became `/store/src/...`; the old catch-all rewrite then answered
those with the HTML shell and a 200, so the failure looked like success.

The shell now declares **`<base href="/">`** as the first element of `<head>`, so every relative
reference and every runtime `fetch('./X')` is resolved from the site root, whatever the URL. There is no
second mechanism to keep in step. Consequences kept on purpose:

* `href="#anchor"` links would navigate to `/#anchor`. There are none in the shell or its chunks (a test
  would not catch a new one — avoid them; use handlers). The SuperAdmin control center, which does use
  `#section` links, is a separate document **without** a `<base>`.
* The DC runtime re-fetches the page URL at boot to recover its exact template text (HTML attribute
  parsing lower-cases `dcProps`). The gateway therefore answers that request — `fetch()`, `Accept: */*` —
  with the shell even for a 404 route, and `support.js` accepts the body whatever the status
  (`LOCAL PATCH 2`). A request that clearly wants something else (script, image, JSON) gets a plain 404.

## 5. Hosting and deployment

| Layer | What the repository configures | Role |
|---|---|---|
| **Vercel** | `vercel.json` (generated), `api/index.js`, `scripts/assemble_public.js` → `public/` | **The live host.** `loumoo.store` answers `Server: Vercel`; the static output is `public/`, `/api/*` goes to the `api/index.js` serverless function. |
| Railway / Express | `Dockerfile`, `railway.json`, `.github/workflows/deploy.yml`, `server/index.js` | A complete second deployment of the same app (API + frontend in one container). `server/index.js` reads the registry directly. |

> The Vercel and Railway accounts reachable from the engineering session that wrote this did not contain
> the LOUMOO project, so the production topology above is inferred from HTTP responses
> (`Server: Vercel`, `x-vercel-cache`) and the repository, and project settings (production branch,
> domains, env vars) could not be inspected.

**What a request gets, in order (Vercel):** `trailingSlash: false` (`/x/` → `/x`), then `redirects`
(legacy aliases, 308, query kept), then a real file in `public/` wins, then `rewrites` (the API function;
`/admin`, `/superadmin` → the control center; each registered route → `index.html`), and anything else →
`404.html` with a **404 status**. `404.html` is the same application shell, so the router draws the
not-found screen. There is **no catch-all rewrite**: a missing script, stylesheet or image under any
path is a 404, visible in the browser's network panel, never HTML with a 200.

**Generated, not hand-edited.** `vercel.json`'s `redirects`/`rewrites`/`trailingSlash` are produced from the
registry. Netlify is no longer used; its `netlify.toml` was removed when it drifted from the registry.

```bash
node scripts/sync_route_config.js          # rewrite them
node scripts/sync_route_config.js --check  # fail if they drifted (also run by tests/unit/routing_deploy.test.js)
node scripts/sync_route_docs.js            # refresh the route map in this document
```

**Adding a route:** add one `def(...)` line in `src/routing/routes.js` (a new shell screen also goes in
`SCREENS` in `build_redesign.py` — `routing_registry.test.js` fails until it is routed or listed under
`unroutedScreens` with a reason), run the two sync scripts, `python build_redesign.py`, and the tests.

**Caching.** `index.html`/`404.html` are always revalidated (`max-age=0, must-revalidate` on Vercel;
`no-cache` from Express). `/Assets/*` are cached for a day. Static files carry `nosniff`.

**Deploying.** Merge to `main`; the host builds with `node scripts/assemble_public.js`. Nothing in the
repository pushes to Vercel. After the first deploy of this change, verify with the checklist in
section 9.

**Canonical host.** The registry's origin is `https://loumoo.store`, but the apex domain currently
308-redirects to `www.loumoo.store` (a Vercel *Domains* setting that lives outside this repository). The
app emits no `<link rel="canonical">` until the project owner decides which host is primary, so it cannot
contradict the redirect; sign-in is not host-sensitive (the session token is first-party and stored per
origin, so a visitor who switches between the two hosts is signed out of the other).

## 6. Admin vs super admin

`/admin` and `/superadmin` are the **standalone control center** (`SuperAdmin/frontend`), published at both
URLs and gated by `SuperAdmin/frontend/js/superAdminGate.js`, which asks `GET /api/v1/me/state` who the
visitor is: `/admin` admits `admin` and `super_admin`; `/superadmin` admits `super_admin` only. That is a
courtesy. The authority is the backend (`SuperAdmin/backend/middleware/superAdminGuard.js`):

* every `/api/v1/admin/*` request needs `admin` or `super_admin`;
* `requireSuperAdminOnly` additionally guards what decides who owns the platform or how it behaves for
  everyone: **role changes, platform settings writes and resets, and the maintenance switch**;
* the generic user update accepts only moderation fields (`first_name`, `last_name`, `city`, `avatar_url`,
  `phone_number`, `status`) — `primary_role` and every other column are refused — and an `admin` cannot
  modify an account that is itself `admin` or `super_admin`; nobody changes their own role.

Before this change `admin` and `super_admin` were interchangeable: an `admin` could promote any account
(its own included) to `super_admin`. `tests/unit/super_admin_role_separation.test.js` pins the fix.

The shell also contains a legacy in-app `superAdmin` screen. It has no entry point and ships seeded demo
data (a fabricated audit entry, default statistics), so it is deliberately **not** routed.

## 7. Security model

* **Routes decide what to show; the backend decides what is allowed.** A customer who types `/admin`,
  `/rider` or `/sell/deliveries` gets at most an empty or error screen: the API refuses every operation
  (`tests/routing/backend_authz.e2e.test.js`: persona × route assertions against the real server).
* **Identifiers in URLs grant nothing.** `GET /api/v1/orders/:id` and `GET /api/v1/deliveries/:id` answer
  404 — the same body as a missing record — to anyone who is not a participant; the handover code is
  readable only by the buyer; rider endpoints need an active registered rider; seller dispatch needs the
  order's seller.
* **Storefronts.** `/store/:slug` shows only live (`ACTIVE`, not `PRIVATE`) stores to the public; any other
  state is indistinguishable from "does not exist". Owner and admins can preview.
* **No private data in the shell.** The HTML is static and identical for everyone. Account state, orders
  and deliveries arrive only through authenticated API calls; the router's `returnTo` carries a path, never
  data.
* **Sessions.** The existing provider and lifecycle are untouched: a first-party bearer token
  (`/api/v1/auth/*`), account state from `/api/v1/me/state`, 401 = signed out, 403 = suspended.
  There are no redirect-based callbacks in the sign-in flow (it is OTP/password in-app), so there is no
  external callback URL to register for this change.

## 8. What is not built, and known defects found on the way

Not built (documented, not faked): **MarketHub** (`/markethub`) and an **agency workspace** (`/agency`).
Unreachable legacy screens left unrouted: `superAdmin` (prototype, seeded data), `sellerPublicPage` and
`publicUserProfile` (no data loader).

Defects found while verifying, outside the routing change itself (see the engineering report for severity):

* `SuperAdminRepository` queries columns no migration defines and, on error, silently serves built-in demo
  rows in every environment — the admin lists can show fabricated data.
* `POST /api/v1/orders` does not enforce `canPurchase` (an unverified account can place an order).
* A store created without a phone number publishes the owner's account phone.
* `DELETE /users/me` followed by `POST /auth/login` signs the deleted account back in.
